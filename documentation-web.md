# Web Platform (Next.js) — Architecture Documentation

## High-Level Architecture Overview

This project uses a decoupled headless architecture. A single, centralized Laravel instance acts as the core business logic engine, data repository, and API gateway. The administrative panel is integrated directly into the backend using Filament PHP. The web client operates independently, consuming the backend purely over a REST API.

```
                      ┌────────────────────────────────────────┐
                      │        Laravel Backend Engine          │
                      │  (Models, Business Logic, DB Migrations)│
                      └────┬───────────────────────────────┬───┘
                           │                               │
    ┌──────────────────────▼──────┐               ┌────────▼──────────────────────┐
    │     Filament PHP V3         │               │     Laravel Sanctum API       │
    │  Administrative Back-Office │               │    (Endpoints & Middlewares)  │
    └─────────────────────────────┘               └────────┬───────────────────────┘
                                                            │
                                                            ▼
                                              ┌─────────────────────────┐
                                              │    Next.js Web Client   │
                                              │  (Stateful Cookie Auth) │
                                              └─────────────────────────┘
```

- **Administrative Operations** — executed server-side, directly over the database models, via Filament.
- **Web Channel** — consumes data via decoupled REST calls from a Next.js Server-Side Rendered (SSR) environment.

## Web Authentication Protocol

Authentication is handled through Laravel Sanctum's **stateful guard**, designed specifically for first-party SPA/SSR clients like Next.js.

```
                     Inbound Auth Request
                              │
                              ▼
                       Is Web Client
                              │
                   [Sanctum Stateful Guard]
                              │
                     Validates CSRF Token
                              │
                    Issues HttpOnly Cookie
                              │
                    Stored by Web Browser
```

**Mechanism:** Stateful Cookie-Based Session Authentication.

**Handshake Sequence:**
1. The client sends a GET request to the CSRF token initialization endpoint (`sanctum/csrf-cookie`).
2. The server responds by setting an encrypted Cross-Site Request Forgery (CSRF) cookie in the client's storage.
3. The client sends login credentials via a POST request, automatically including the CSRF token header.
4. The server validates the credentials and authenticates the user's web session.
5. The server issues an HttpOnly, Secure, SameSite=Strict session cookie.

**Security Profile:** Protects the client application from Cross-Site Scripting (XSS) attacks by preventing malicious JavaScript from reading or extracting the authentication token.

## Chapa Payment Integration Workflow

To safeguard transaction totals, payment processing follows a strict server-to-server pattern. The Next.js client is never permitted to communicate directly with Chapa's initialization or validation gateways.

```
Next.js Client                        Laravel API Backend                Chapa Gateway
          │                                   │                                │
          │ 1. Initiates checkout request     │                                │
          ├──────────────────────────────────│                                │
          │                                   │ 2. Generates unique text reference
          │                                   │    Marks order as pending    │
          │                                   │                                │
          │                                   │ 3. Issues HTTP call to gateway │
          │                                   ├───────────────────────────────│
          │                                   │                                │
          │                                   │ 4. Responds with payment url   │
          │                                   │───────────────────────────────┤
          │ 5. Returns payment URL to client │                                │
          │──────────────────────────────────┤                                │
          │                                   │                                │
          │ 6. Redirects user to checkout     │                                │
          ├───────────────────────────────────────────────────────────────────│
          │                                   │                                │
          │                                   │ 7. Customer pays via local app │
          │                                   │    (Telebirr, CBE Birr, Card) │
          │                                   │                                │
          │                                   │ 8. Asymmetric webhook callback │
          │                                   │───────────────────────────────┤
          │                                   │                                │
          │                                   │ 9. Verifies signature/status   │
          │                                   │    Transitions status to paid │
```

### Detailed Operational Phases

**Phase 1 — Request & Locking**
The client clicks the payment button, transmitting the target `order_id` to the secure backend. Laravel fetches the order details, computes the final total, generates a unique text reference key (`tx_ref`), and locks the order status to `pending`.

**Phase 2 — Gateway Handshake**
Laravel makes a server-to-server request to Chapa's API endpoint, passing the generated reference string, transaction total, customer data, an explicit frontend fallback URL, and an immutable webhook callback path pointing to your Laravel API.

**Phase 3 — UI Redirection**
Chapa responds with a transaction object containing a secure `checkout_url`. Laravel forwards this URL to the calling client. **Next.js performs a standard browser location redirect.**

**Phase 4 — Verification & Webhook Execution**
The user authorizes the transaction on Chapa's portal using their payment method (e.g., Telebirr, CBE Birr, or a credit card). Once the funds are collected, Chapa issues an asynchronous server-to-server webhook callback request to your Laravel backend. The payload contains an authorization header signature value (`x-chapa-signature`). Laravel interceptors match this string against the system configuration to authenticate the request's origin. Once verified, the order status changes to `paid`, which automatically triggers transactional emails and stock deductions.

## Filament Admin Panel Boundary Controls

Filament acts as an internal micro-application inside the main Laravel ecosystem. While it leverages your core Eloquent data models, it operates under separate access restrictions to keep standard users isolated from administrative functions.

```
Inbound Request to /admin Panel
              │
              ▼
   [Filament User Interface Guard]
              │
      ┌───────┴───────┐
      ▼               ▼
Has Admin Access   Standard Customer User
      │               │
  [Granted]       [Access Denied — 403 HTTP Error]
```

- **Panel Segregation** — access rules are embedded directly into the central user model. Standard users hitting customer routes receive standard JSON responses, whereas administrative accounts are authorized to pass through Filament's interface guards.
- **Interface Decoupling** — Filament resources manage model interactions on the server side using asynchronous PHP components. This keeps the admin panel completely independent of any JavaScript packages or configurations used by the Next.js web application.

### NGINX Configuration (Single-Server, Pre-Scale)

For the current single-server deployment (on Yegar Host), NGINX runs as a standard Laravel web server — handling PHP-FPM routing and caching static assets (CSS, JS, images) with long browser-cache expiry. It is **not** configured as a load balancer yet; that conversion is deferred until a second server is added.

The tested, corrected configuration:

```nginx
server {
    listen 80;
    listen [::]:80;

    server_name yourdomain.com www.yourdomain.com;
    root /var/www/your-laravel-project/public;
    index index.php index.html index.htm;

    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header X-XSS-Protection "1; mode=block" always;
    add_header X-Content-Type-Options "nosniff" always;

    charset utf-8;

    location / {
        try_files $uri $uri/ /index.php?$query_string;
    }

    location = /favicon.ico { access_log off; log_not_found off; }
    location = /robots.txt  { access_log off; log_not_found off; }

    error_page 404 /index.php;

    location ~ \.php$ {
        fastcgi_pass unix:/var/run/php/php8.3-fpm.sock;
        fastcgi_param SCRIPT_FILENAME $realpath_root$fastcgi_script_name;
        include fastcgi_params;
    }

    location ~* \.(jpg|jpeg|png|gif|ico|css|js|woff|woff2|svg)$ {
        expires 365d;
        add_header Cache-Control "public, no-transform";
        access_log off;
    }

    location ~ /\. {
        deny all;
    }
}
```

**When a second server is added later**, this same file converts to a load balancer by replacing the single `fastcgi_pass`/`root` block with an `upstream` block listing multiple backend servers, and switching `location /` to `proxy_pass` against that upstream — a small, well-contained change, not a rebuild.

## Local Development Environment (Laravel Sail on Windows)

Running Redis and Nginx natively on Windows is not recommended for this stack — Redis has no officially supported Windows build, and more critically, **Laravel Horizon cannot run on native Windows PHP at all**, because it depends on the `pcntl` PHP extension for its async process-signal handling, and `pcntl` is not available on Windows builds of PHP. The standard fix — recommended by Laravel's own maintainers — is to run the backend inside a Linux environment.

Rather than hand-writing a Docker Compose file from scratch, we build on **Laravel Sail** — Laravel's own official Docker-based development environment, which has been the framework's default recommended local setup since its introduction in December 2020. Sail already provides Docker Desktop/WSL2-backed PHP, MySQL, and Redis containers out of the box; we extend it with two services Sail doesn't include by default: a Horizon queue worker container and an Nginx reverse proxy.

```
┌────────────────────────────────────────────────────────┐
│               Your Windows Machine (Host)                │
│                                                            │
│  ┌──────────────────────────────────────────────────┐    │
│  │      Docker Desktop Engine (powered by WSL 2)     │    │
│  │                                                    │    │
│  │  ┌───────────────┐ ┌───────────────┐ ┌────────┐   │    │
│  │  │ laravel.test  │ │ horizon       │ │ redis  │   │    │
│  │  │ (Sail's PHP   │ │ (same image,  │ │ (Sail  │   │    │
│  │  │  container)   │ │  runs Horizon)│ │ service)│  │    │
│  │  └───────▲───────┘ └───────▲───────┘ └───▲────┘   │    │
│  │          │                 │             │        │    │
│  │  ┌───────┴─────────────────┴─────────────┴─────┐  │    │
│  │  │      nginx (added — not part of default Sail) │ │    │
│  │  └───────────────────────▲───────────────────────┘ │   │
│  └──────────────────────────┼──────────────────────────┘  │
│                              │                             │
└──────────────────────────────┼─────────────────────────────┘
                                │
                     [ Next.js Web Client ]
```

### Setup, in order

1. **Install Sail into the existing project** (this project already exists — Sail is added as a dependency, not scaffolded fresh):
   ```
   composer require laravel/sail --dev
   php artisan sail:install
   ```
2. **When prompted for services**, select `mysql` and `redis` — these are two of Sail's official supported service options (the full list also includes `pgsql`, `mariadb`, `memcached`, `meilisearch`, `typesense`, `minio`, `mailpit`, `selenium`, `soketi`, but only MySQL and Redis are relevant to this architecture).
3. This generates a `docker-compose.yml` with two services already configured correctly: `laravel.test` (the PHP/Composer/Node container, which serves the app directly on port 80 by default) and `redis`.
4. **Add a `horizon` service** to the generated `docker-compose.yml` — it reuses the exact same build context as `laravel.test`, differing only in its startup command (`php artisan horizon` instead of serving HTTP).
5. **Add an `nginx` service** — this is the one piece Sail does not include by default. It sits in front of `laravel.test` as a reverse proxy/load balancer, matching the architecture doc's requirement.
6. Update `.env`: Sail's convention is `DB_HOST=mysql`, `REDIS_HOST=redis`, `QUEUE_CONNECTION=redis` — matching the container hostnames, not `127.0.0.1`.
7. Start everything:
   ```
   ./vendor/bin/sail up
   ```

### Why this is better than a fully custom Compose file

- **Less to maintain** — Sail's PHP image is officially maintained by Laravel and already includes Composer, Node, and the correct PHP extensions for the framework version in use.
- **Still solves the original problem** — the `laravel.test` container is Linux-based, so `pcntl` and Horizon work correctly, exactly as a fully custom Docker setup would achieve.
- **Production parity retained** — the same container images run locally and on the production Linux host (the DigitalOcean Droplet or AWS EC2 instance described above).
